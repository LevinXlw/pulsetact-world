# 项目开发规范：视觉还原

初版日期：2026-10-22；当前修订：2026-10-26（执行规范 v1.1，现实细节优先澄清）。适用于 Pulsetact World 后续所有校园、建筑、环境、人物及载具的新增、重建、优化和验收。

## 1. 验收目标

2026-10-23 用户确认：**“做成和真实场景一样真实的3d模型。”** 2026-10-25 用户要求借鉴所提供 demo 的画风制作 Pulsetact World，先以 MIT 主楼为样板，并明确**颜色保持项目原有风格，不采用 demo 的蓝白色调**。2026-10-26 用户进一步明确：**“我还是需要尽可能地还原现实细节。”** 这一澄清同时约束形体、构件、空间与材质表面；此前将 demo 画风理解为允许降低现实材质和可见细节的表述不再适用。当前材质、光照与氛围按第 3 节及 [诗意校园 · 幻想写实](pulsetact-poetic-art-direction.md) 执行，以现实细节优先。

建筑几何、地形道路、景观布局和近景构件应有实景依据；材质也须尽可能保留可观察到的石材分缝、颗粒、色差与磨损，玻璃深度及环境反射，铺装、收边和接地层次。风格化不能以抹平表面、涂平玻璃或删除可见细节为手段；光影、氛围与色彩组织不得损害现实真实性。不要求与实拍逐像素一致，但能认出建筑、轮廓相似、比旧白模精细都只是过程中的进展，不能单独作为最终完成标准。几何、空间与材质均按实景验收。

此前“一些细节尺寸有误差可以接受”的容差仍有效：无法实测的局部尺寸可以合理估算。它只放宽尺寸精度，不放宽真实感，也不意味着可以降低建模、材质或场景完整度。不要求施工图级测量，但应明确哪些部分基于测绘、哪些依据照片推定。

本规则是长期开发规范，不仅适用于 MIT Stata Center，也适用于 BU、UMD、UPenn、University of Arizona 等现有区域以及未来新增校园。根目录 [AGENTS.md](../AGENTS.md) 是开发者和 AI 代理读取本规范的入口。

## 2. 必须保留与允许近似的内容

| 对象 | 必须保留的视觉特征 | 可以合理近似的内容 |
| --- | --- | --- |
| 建筑整体 | 体块比例、高低关系、相互位置、倾斜方向、退台、曲面、屋顶和外轮廓；各朝向真实的开口组织 | 不改变真实观感的局部尺寸偏差、不可见构造 |
| 建筑构件 | 门窗的深度、框体与分格，檐口、窗台、栏杆、台阶、屋面收边、悬挑和入口的结构层次 | 非关键截面、紧固件和装饰的小尺寸；不能因此省略可见构件或把应有深度的窗洞改成平面贴片 |
| 道路与地形 | 道路走向、宽窄关系、坡度和高差、路缘、过街连接、建筑接地、河岸及庭院关系 | 不改变空间体验的局部尺寸和铺装分缝偏差；不能把坡地做平或将道路、绿带连成一整片 |
| 材质与景观 | 真实材质分区、尺度、颜色、粗糙度、微表面与反射；玻璃、金属、砖石应有不同质感；树群尺度、疏密和层次应接近实景 | 无须逐块复制每块砖的磨损或每片树叶，但应保留相应质感，避免明显重复、拉伸、接缝和平涂替代 |
| 室内复原 | 在本轮约定范围内，参考可确认的空间组织、层高观感、主要开口与标志性设施 | 家具小构件、隐藏结构及未测量的局部尺寸；未知布局应标为推测 |

不设一个适用于所有构件的统一误差百分比。是否可接受，以正常观察与游玩时是否损害真实感、整体比例或空间体验判断。明显改变主楼轮廓、把坡路做平、遗漏关键建筑或将标志性曲面替换成普通方盒，不能以“尺寸允许误差”为由接受。

## 3. 画风与真实场景的关系

2026-10-26 澄清后的美术方向为 [诗意校园 · 幻想写实](pulsetact-poetic-art-direction.md)。保留项目原有的暖白/米白石材、绿色植被、自然日光与蓝绿色水面，尽可能还原现实中的构件与材质细节。借鉴 demo 的清朗、柔和氛围与明暗组织，但不以减少石材微纹理、磨损、污渍或铺装分缝来取得“干净感”，也不压平真实光照下的构件层次。纹理和磨损须有实景依据，既不能无故省略，也不人为堆砌随机污渍。首次制作范围仍为 MIT 主楼 Building 10 / Great Dome 朝 Killian Court 的主体与主立面，以及支撑该视野的既有环境，不能由此声明全校园已经完成风格迁移。

实景照片继续用于核对建筑比例、穹顶曲线、柱列、窗洞、檐口、道路、树位与地形。demo 只提供美术语言，不提供 MIT 几何、布局或材料事实；其蓝白配色、夜空、白色植被、破败遗迹与水淹场景不纳入本轮主题。保留现实校园的草坪、步道和出入口，水面效果限于已有真实水域。

验收同时对照实景依据与当前美术定义，不以风格化接受通用低模、统一重复窗格、平涂玻璃、缺失的构件深度或明显失真的比例。按实际观察距离保留近景微表面、窗洞、框体、柱础、台阶、铺装与接地层次；只能过滤渲染混叠和无依据的噪点，不能把真实细节一并抹去。画风应在正常游戏光照和步行视角中成立，不能只依赖离线渲染、滤镜或单个有利机位。G0–G4、可编辑源、资源分级、碰撞与实际游玩验证继续执行，技术通过与视觉通过分别报告。

## 4. 开发顺序与参考依据

1. 明确本轮建筑或区域范围，整理可获得的多角度实景照片、校园地图和已有地形、测绘数据。保存参考来源，区分真实资料与概念设计。
2. 先校准整体轮廓、体块关系、道路和地形。优先修复一眼可见的偏差，再做材质与微小构件。
3. 按实景补齐构件层次、入口、窗洞进深、屋顶与近景细节，建立适合砖石、玻璃、金属等材质的表面表现，使建筑与街面自然衔接。
4. 在玩家实际可接近的观察距离检查材质尺度、反射、阴影、接地与细节；以完整模型的真实感目标为基准制作移动端或低画质版本，明确各档资源取舍。
5. 在实际游戏中对照实景验收；主形体、材质或场景真实感有明显差距时，返回对应环节修正。不能靠增加面数、堆贴图或调整滤镜代替。

Blender、Three.js、程序化建模或 AI 生成工具均是实现手段，工具名称和生成方式不构成质量达标的证据。生成或导入资产同样需要按参考校正形体、材质与场景适配。

有可靠 CAD、扫描或测绘资料时应合理利用；没有时，按公开照片和已知空间线索进行视觉重建。**原始 CAD、精确尺寸不是一般开发的前置条件。** 未确认的小尺寸可合理估计，无需逐项要求用户确认；会显著改变建筑识别特征或场景布局的未知信息需要单独核对。

对可能影响验收的推测说明依据和范围即可，继续推进有依据的重建。不得将照片估算标为“实测精确复刻”，也不得把“缺少 CAD”或“局部尺寸允许误差”当作降低视觉真实感的理由。

## 5. 视觉与游玩验收

- **整体与多方向**：检查本轮范围的整体现状、主要正面、侧面、背面和普通步行视角，不能只依赖一个有利机位。
- **实景对照**：将游戏画面与相近朝向的实景照片并列检查，核对几何比例、材质、构件层次和周边环境；仅“认得出”不足以通过。照片与游戏若非同机位，需说明，不伪称精确配准。
- **近景质量**：在实际步行视角检查窗洞进深、框体、屋面收边、台阶、路缘和接地关系；修复悬空、穿插、破面、闪烁、明显贴图拼缝及不真实的重复纹理。
- **材质与光照**：检查砖石尺度与凹凸、玻璃深度与反射、金属粗糙度和反光、遮蔽与接触阴影；不得通过过曝、浓雾、过暗或远景构图掩盖模型问题。
- **可玩性**：视觉模型与碰撞、地面高度一致，正常路线、台阶和入口不因建模优化而失效。
- **前后对照**：保留可追溯的旧版依据。比较几何和材质时尽量固定相机与光照；有变化时明确说明。使用“修改前／本轮版本”等直接标签，不用含义模糊的百分比表示完成度。
- **证据真实**：提交实际导出模型与实际运行画面。概念图、离线效果图、独立模型查看器和游戏截图分别标明，不能相互替代为验收证据。
- **性能取舍**：低画质和移动端优先精简远处或不可见的次要细节，保留真实轮廓、材质分区、空间层次和可行走区域。明确不同质量档的取舍，不能用手机预算倒推完整模型只需粗糙形似；检查加载、稳定性和资源释放。浏览器模拟检查不等于真机验证。

构建和自动测试通过只证明相应技术检查通过，不能代替实景视觉对照。阶段模型可以交付供查看，但应明确尚存的真实感差距，不能因“有提升”“已接入”或技术测试通过就称为达到最终质量。是否完成，按本轮约定范围是否达到上述视觉与游玩标准判断；不额外要求还原未约定的完整室内、隐藏结构或每个微小构件。

## 6. 与历史文档的关系

本规范是当前项目的视觉还原标准，替代 2026-10-22 版本中“只需要形似”作为最终验收目标的表述。旧需求中的艺术化压缩、白模范围、画风与质量描述，若与本规范冲突，以本规范为准。历史交付记录保留其原始事实；包括 Stata、Baker、Maseeh 在内的既有模型须按新标准复核，不能自动认定已达标。用户后续明确调整的要求优先，并应同步更新本规范和根目录入口。

## 7. 标准版本与工具职责

本次执行规范版本：**v1.1 / 2026-10-25**。第 1–6 节的建筑与空间还原目标及第 3 节最新画风要求共同有效；以下条款把目标落实到生产与交付。适用于建筑、道路地形、景观、室内、人物与载具；虚构道具以已确定的设计参考、真实尺度和材料逻辑验收，不伪称实物复原。

默认制作链路：**实景与空间资料 → 形体校准 → 可编辑模型与 PBR 材质 → 游戏资产导出 → Three.js 实际场景 → 视觉、交互与性能验收**。

| 环节 | 默认职责 | 边界 |
| --- | --- | --- |
| 地图、测绘、照片 | 确定位置、高差、体块、立面与材料依据 | 记录年代、朝向及推测部分；AI 补出的视图不能作为实景证据 |
| Blender / 可编辑建模母版 | 重点建筑、异形构件、近景道具的形体、拓扑、UV、材质与可动部件 | 地标与复杂近景资产默认保存可编辑母版；调用 Blender 或保存为 .blend 本身不证明重建完成 |
| 程序化生成 | 数据驱动的地形道路、已校准的重复构件、植被布置与批处理 | 可作为正式生产方式，但参数和生成规则必须可追溯、可复现；不得用同一通用立面替代不同建筑 |
| Three.js | 场景装配、灯光反射、加载与分级、动画、碰撞和交互 | 运行时补丁不能长期掩盖模型本身的错误；仍可承载有依据的程序化几何 |
| Tripo 等生成工具 | 可选的候选几何、装饰与道具初稿、材质探索 | 生成结果经过相同质量门槛；不视为真实测绘、建筑布局来源或自动合格资产 |

2026-10-25 工具接入约定：日常 Blender 场景检查、建模和材质迭代使用 MCP，操作前确认当前文件与场景；可复现的批量生成、烘焙和导出仍可使用 bpy 脚本。母版、GLB 和 Three.js 运行验收职责不变。具体安装、连接与实测状态见 [Blender MCP 工作流](blender-mcp.md)。MCP 是控制与反馈通道，不是视觉质量证明。

每轮说明属于“形体重建”“构件补全”“材质精修”“运行时表现”中的哪些工作。若沿用旧形体，仅加倒角、贴图或细节，必须按实际工作标注，不能称为完成整楼真实重建。主形体有误时，优先修改或重建源形体，不以保留旧网格作为质量目标。

## 8. 必须执行的五道检查

这些检查由开发者在授权范围内自检并记录，不新增逐阶段等待用户批准的流程。发现问题回到相应环节；不确定的小尺寸按第 4 节合理推定并继续。

| 检查 | 必须形成的成果 | 不能进入“验收通过”的情形 |
| --- | --- | --- |
| G0 参考与范围 | 资产 ID、本轮覆盖区域/立面、地图定位、多方向照片、关键特征清单、旧版基线、未知部分 | 只有概念图；没有确认入口、主体或相邻道路的关系 |
| G1 形体与接地 | 中性材质的多角度检查；主要比例、体块、层数、开口、坡度、屋顶与空间位置校准 | 主体比例或朝向明显错误；缺少标志性构件；楼、路、台阶、坡地互相脱离 |
| G2 构件与材质 | 门窗进深、框体、收边、近景层次、UV 与材料分区；中性光和游戏光下检查 | 靠贴图画出应有的开口；玻璃、金属、砖石表现无法区分；明显拉伸、拼缝或烘焙阴影冲突 |
| G3 实际游玩 | 导出并接入真实场景；多方向、步行视高及可接近近景截图；连续路线/动作验证 | 只在 Blender 或独立查看器成立；门口被碰撞挡住；穿墙、悬空、穿地、错误坐姿或肢体穿插 |
| G4 分级与交付 | 完整模型、移动/低画质版本及差异说明；资源与性能记录；可复现源文件与剩余问题 | 只用面数、截图美化或测试通过证明真实感；手机档改变路线；交付无法追溯或无法重建 |

G1 先确认形体再投入大面积贴图；G3 必须加载本轮实际导出的资产。单项明确失败时，即使其他项通过，也只能标为阶段版本。

## 9. 模型、材质与导出约定

### 9.1 坐标、结构与可编辑性

- 资产尺寸以米记录。新资产导出到游戏采用 Y 向上；角色/载具约定 +Z 为前方，Blender 等工具的轴向转换在导出或单一适配处完成。已有 GIS、地形和角色原生坐标不得盲目改轴，保留并记录其 local-to-world、朝向和缩放。
- 标明原点、包围盒、地面接触面。建筑保留稳定的地图锚点；门、轮、转向部件等使用正确的局部旋转轴，不以缩放整物体代替真实尺寸校正。
- 按功能分离地面、可动门叶、门框、玻璃、碰撞体、交互点等。批处理不能把需要独立运动或交互的构件焊死，也不能重复保留旧模型造成穿插和闪烁。
- 可编辑母版可以是 .blend，或带参数、数据源与生成步骤的程序源；重点异形建筑和复杂近景资产默认提供 .blend。不得只交付无法解释来源的最终网格。
- 导出前检查有限坐标、退化面、重复面、法线、平滑/硬边及 UV；有法线贴图时检查切线表现。开放的窗洞、栏杆和薄片并不一律要求“封闭网格”，按实际构造判断。
- 正式 Web 资产优先 GLB/glTF；程序化资产保留可复现的构建方式。不得依赖个人磁盘绝对路径或本机未提交的隐藏资源才能显示。

### 9.2 几何与表面的分工

- 主轮廓、洞口、窗框/窗台进深、台阶、栏杆、悬挑、曲面转折等影响轮廓、遮挡、碰撞或近景光影的内容使用真实几何。
- 不改变轮廓的砖面细纹、细小磨损与微表面，可通过正常比例的 Normal/Roughness/AO 等表达；不要求逐砖逐螺钉建模。
- Base Color 不烘入定向阳光、镜面高光或固定环境倒影；AO 与表面色分开控制，避免与运行时阴影叠成脏黑边。
- Base Color 按颜色纹理处理，Normal、Roughness、Metallic、AO 按数据纹理处理；导出后在游戏中确认通道与法线方向，不能只检查文件存在。
- 每类材质记录真实尺寸与贴图覆盖范围，使相邻建筑的砖、石板、木纹尺度一致。贴图分辨率由实际覆盖面积和观察距离决定，不统一堆到 4K/8K。
- 玻璃必须结合玻璃层、框体、遮蔽和合理反射判断；有可进入室内时再协调透射、室内亮度和背后结构。不能一律用透明材质，也不能用一整块平蓝色替代所有玻璃。
- 用实际游戏的光照、曝光和色调映射复核。增加反光、AO、雾或后期效果不能修复错误几何。

### 9.3 人物、载具与交互资产

- 分别验证静止、移动、加速、转向、召唤/收起及恢复步行；检查轮胎接地、旋转轴、手脚接触点、目光方向、手掌握姿和衣物穿插。
- 姿态叠加必须能恢复原动画，多帧运行不能累积旋转或漂移。骨骼数值测试与近景视觉检查分别记录。
- 模型轮廓与碰撞空间相适配；高速移动检查薄墙、拐角、坡面、桥岸和狭窄入口。悬浮类工具的可通行区域与飞行能力须明确，不借模型悬浮绕过未实现的地形规则。
- 不以一张远处骑乘截图认定近景骑姿和接触已经合格。

## 10. 视觉验收与版本状态

每项交付同时提供技术验证状态与视觉验证状态，二者不可互相代替。

- **制作中**：参考、形体或材质仍在制作。
- **阶段可试玩**：已接入游戏，但视觉、性能或部分目标设备仍有明确缺口。
- **范围内验收通过**：本轮声明范围通过 G0–G4，问题清单不存在阻断项；不代表其他立面、室内或整个校园同时完成。

验收资料须包含：

1. 地标/建筑的环境全景、主要正面、左右斜视、可接近背面及入口/窗框/接地近景；无法取得的实景方向标为未知，不能用生成照片补充成“证据”。一般道具至少检查正、侧、背及使用姿态。
2. 实景参考与游戏画面成对排列。记录机位、视场角、画质、设备、光照与资产版本；不同机位或不同季节明确注明。
3. 保留正常游玩 HUD/镜头的可用性检查；另行提供无遮挡细节图。相机过远、人物遮挡或 UI 遮挡导致看不清，须补图，不能因此跳过检查。
4. “修改前 / 本轮版本”固定标签；滑动对比说明左右分别是什么，不用 0% / 100% 暗示完成程度。对照不能用不同相机、曝光或质量档隐瞒退步。
5. 指出具体剩余差距、影响范围与下一步修正，不写没有依据的“95% 还原”。局部通过可单独记录；关键体块、入口、高差、材质类别或近景构造明显失真时，整体不能通过。
6. 固定记录代码提交或工作区快照标识、资产 SHA-256/生成参数与截图对应关系。源模型、导出和截图不一致时重新核对，不沿用旧验收。

## 11. 完整模型、分级与运行预算

先保留完整模型与材质，再制作运行分级。LOD 表示确实有记录的细节层级；**相同几何仅去除纹理的 mobile-source 文件是加工中间件，不等于减面 LOD**。降低 DPR、减少阴影、简化材质、减少几何必须分别描述。

预算在每个资产/场景开工时登记，按实测调整，不设“多于多少面才算精细”的门槛：

| 项目 | 必须记录 |
| --- | --- |
| 几何 | 完整源模型、导出资产和运行可见几何分别计数；三角形、节点、材质/primitive 数；共享与重复实例 |
| 纹理与下载 | 分辨率、通道、格式、传输字节；解码后纹理占用估算，注明估算方法，不能用文件大小冒充显存 |
| 运行 | 实际 draw calls、加载/切换时间、帧时间中位数与 P95、错误/崩溃/资源释放情况 |
| 条件 | 设备/GPU、浏览器、分辨率/DPR、画质档、路线、采样时长及并发负载 |
| 分级 | 具体删减内容、切换条件、轮廓/材质分区/碰撞与可行走区域是否保持一致 |

默认体验目标为桌面向稳定 60 FPS 优化、移动端向稳定 30 FPS 优化；对应目标设备、画质和场景必须列明。这是制作目标，不是当前已经达到的承诺；不得拿 headless 或浏览器手机模拟值替代真机结论。尚未完成真机检查的交付明确标记“移动真机待验证”。

超出预算时优先采用分区/按需加载、实例化、材质合批、远景分级与纹理优化。Meshopt、Draco、KTX2 等只在对应资产加载器、解码资源和目标浏览器实际验证后启用；不得把其他页面已有的解码器写成全项目已经支持。保留完整母版，不能通过破坏地标轮廓、删除真实入口、填平坡度来压缩预算。

## 12. Tripo 的项目使用规则

定位：**可选的离线资产制作助手**。它不参与玩家运行时请求，游戏仍使用已验收的本地/部署资产。

| 资产任务 | 默认选择 |
| --- | --- |
| CDS、Questrom、Stata 等地标主体；重复且有规律的立面 | 以照片/地图校准的 Blender 或可编辑程序化建模为主；Tripo 候选只能作辅助，不直接认定为建筑还原 |
| 道路、坡地、岸线、轨道、校园整体布局 | 使用空间资料与可控几何，不使用生成结果作为布局或高程依据 |
| 独立雕塑、装饰、自然形态小物件、虚构道具 | 可优先试用 Tripo 生成候选，再修形、拆件、整理拓扑和材质 |
| 摩托等机械/互动资产 | 可试作外观初稿；车轮、车把、活动件、接触点、尺度与绑定须明确校正 |
| 已经校准的模型表面 | 可试 AI 材质候选，检查几何未被改坏、材质分区正确、贴图无烘焙高光与重复伪细节 |

以上是本项目的工程分工判断，不是对生成器实测成功率的声明。多视图可以提供更多约束，不能证明背面、开口、构造和尺寸已经真实。

所有 AI 候选必须保留：服务/模型版本、任务 ID（如有）、生成日期、提示词与输入来源、生成原件、清理后的母版、手工修正清单和授权记录。公开参考资料可用于视觉研究，不自动意味着可上传到第三方或作为纹理再分发；分别记录输入许可和输出许可。

截至 2026-10-25，官方资料列出文本、单图/多视图生成、重拓扑、PBR 与 GLB/FBX 等导出，并提供 Blender 衔接方式。功能是否在当前账号和所选模型开放，以实际操作与导出为准：[官方 FAQ](https://www.tripo3d.ai/product-doc/support/faq)、[导出说明](https://www.tripo3d.ai/product-doc/export-and-integration/export-dcc)、[PBR 说明](https://www.tripo3d.ai/product-doc/module-post-processing/texture-pbr)。

正式引入前记录生成时的套餐、私有/公开设置及允许用途。官方价格说明将付费且设为私有的模型列为完整商用/用户所有，具体适用仍核对当时条款和素材本身的权利；不因“有账号”直接认定全部历史输出适用同一授权：[套餐与授权](https://www.tripo3d.ai/product-doc/getting-started/pricing-credits)、[服务条款 §5.2](https://www.tripo3d.ai/terms)。

建议先以少量代表资产进行试作，比较同一目标下的 **生成 + 重试 + 修形 + 材质 + 绑定/碰撞 + 导出 + 验收** 总成本，记录实际额度和工作时间。只有通过本规范且总工作量确实下降的类型才扩大使用；无须先把 Tripo API 集成为生产依赖。

## 13. 每次资产交付的最小记录

记录归入该资产已有的 manifest/说明文件或版本化文档，格式可沿用已有 JSON；以下字段必须能找到。临时截图可在 output/，但验收结论、来源与关键证据应有持久副本或可访问的归档，不能只指向被忽略、不可恢复的本机文件。

- 身份与范围：assetId、版本/日期、真实对象或虚构设计、本轮区域/立面/构件、当前状态。
- 依据：照片/地图/测绘来源、年代和朝向、输入/输出授权、测量/照片推定/设计创作的区分、未知项。
- 制作：采用的工具与版本、实际修改类别、母版/源代码/生成数据、构建步骤、导出文件及 hash、坐标转换和尺寸。
- 渲染与交互：材料/贴图说明、门/轮等部件及锚点、碰撞与动作约定、完整与低档版本差异。
- 资源与验证：各档预算和实测、G0–G4 分项结果、游戏入口与测试路线、对应版本的实景对照和截图、技术检查结果、真机/模拟区分。
- 结论：已通过范围、阻断问题、剩余偏差及下一步，不把历史模型或本轮功能上线自动标成视觉验收通过。

既有资产不因此自动合格，也不要求为了整理规范立即重写全库；后续每次修改按本规范补齐本轮范围的记录，并保留旧记录的原始事实。
